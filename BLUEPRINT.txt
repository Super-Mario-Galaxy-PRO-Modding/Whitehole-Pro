3. CODE CONVENTIONS (enforced by review, not by a linter)
--------------------------------------------------------------------------------

 - C++20, no compiler extensions. `[[nodiscard]]` on anything that returns a
   value the caller must not drop; `noexcept` where it genuinely cannot throw
   (the camera math is all noexcept).
 - Comments are the deliverable, not filler. Every non-obvious decision gets a
   comment that says WHY, in plain English, usually 2-5 lines above the code.
   The camera code is commented at essay length because it is all reverse
   engineered; keep that tone.
 - ASCII only in sources: use "--" and "==" instead of em/en dashes. The header
   jpName strings are the one exception (they are game data).
 - Namespace layout mirrors the folder: whitehole::math / io / smg / render /
   edit / db / app.
 - Style of a feature here: small typed value struct + free functions over a
   table class (see CameraParamTable + cameraPreviewParams + solveGameCameraPose)
   rather than a god-object. Do not add virtual inheritance.
 - Never break byte-exact round trips: a table that was not edited must save
   back identical (BCSV writer may only append alignment padding). Same rule for
   RARC. If your change makes an untouched file differ, that is a bug.
 - The GUI is immediate-mode ImGui inside a Win32 shell; state lives in
   `struct EditorState` (gui_win32.cpp:131), panels are free functions taking
   `EditorState&` (e.g. drawObjectsPanel at gui_win32.cpp:2077). The editor lives
   in runGui(executable, initialFile) (gui_win32.cpp:4835) - its `EditorState
   state;` is at :4947 and the per-frame work (layout pass at :5121) follows.
   Mutations go through markDirty() (gui_win32.cpp:1263) + refreshViewport()
   (gui_win32.cpp:715) + the UndoStack.
   User-visible errors go through pushToast(state, text, error)
   (gui_win32.cpp:590). Viewport child window placement: syncViewportChild
   (gui_win32.cpp:3300). Fonts/theme apply once at boot right after
   ImGui_ImplWin32_GetDpiScaleForHwnd, with a guard that clamps implausible DPI
   readings to 1.0 - do not load fonts before that.

4. THE BCAM SUBSYSTEM - REAL API (cpp/include/whitehole/smg/camera_param.hpp)
--------------------------------------------------------------------------------

 Everything below is copied from that header. It is the contract: write the GUI
 against exactly these names. Section 8.0 lists the fictions that got reverted.

 Constants / enums
   kCameraVersionSmg1 = 196630, kCameraVersionSmg2 = 196631 (row `version`)
   kCameraParamPath = "/Stage/camera/CameraParam.bcam" - RarcArchive lookups are
       case-insensitive, which is how SMG1's all-lowercase path still resolves.
       StageArchive keeps the path as stored (cameraTablePath_) to write back.
   cameraVersionForGame(int gameType) -> gameType == 1 ? SMG1 : SMG2
   enum class CameraContext : invalid, cube, spawn, event, group, other (c: s: e: g: o:)
   enum class CameraFieldScope : general, game, event
       general = every camera; game = gflag.* (c:/g:/s: only); event =
       eflag./evfrm/evpriority/camendint (e: only).
       NOTE: there is NO kAll / kZoneOnly / kStageOnly / kBossOnly - the reverted
       draft invented those. "Does this field apply to this camera" is
       cameraFieldApplies(scope, context).
   enum class CameraFieldGroup : identity, framing, behavior, flags
   enum class PoseSupport : std::uint8_t { exact, spherical, none }

 Camera id
   struct CameraId { CameraContext context; int32_t number{-1}; std::string name;
                     std::string raw; }
   parseCameraId(sv) never fails (unrecognised prefix -> invalid).
   formatCameraId() canonicalises (c:/s: go through "%04x", lowercase padded).
   describeCameraId() -> friendly English label; unknown ids echo the raw text so
   a UI label is never empty.
   cubeCameraIdForArg(objArg0) / spawnCameraIdFor(cameraSetId) reproduce the
   game's printf: Obj_arg0 15 -> "c:000f", CameraSetId 60 -> "s:003c".
   cameraContextLabel(context) -> "Camera area", "Spawn point", ...
   eventCameraIdFor(jpEvent, setId, subIndex) -> the e: id the game itself
   writes: "シナリオスターター",5,1 -> "e:シナリオスターター:005:01番目". The
   set id is %03d and the sub-index %02d plus the literal 6-byte "番目" that
   describeEventId() strips on the way back. THIS is the function that makes a
   scenario-starter camera authorable: the stored text is Japanese and the panel
   font has no CJK glyphs, so an author who has to TYPE an e: id cannot.
   cameraIdExists(table, id) -> is this id already in the table? Compares the
   PARSED id, so "c:000F" matches a stored "c:000f"; an unparseable or empty id
   is never a duplicate (it must not block a half-typed one).
   nextFreeEventCameraId(table, jpEvent, setId) -> the lowest ":NN番目" not
   already stored, for that event + set id. Scans 00..99 and falls back to 00.

  The known-name dictionaries (ADDED for the id composer; were file-private,
   which is WHY e: rows were display-only)
   struct KnownCameraEvent { std::string_view jp, en; bool needsId, needsSub; }
   cameraKnownEvents()          -> e: event names, LaunchCamPlus order
   cameraKnownOthers()          -> o: names (needsId/needsSub always false)
   cameraGameCreatedEvents()    -> cameras the game BUILDS at runtime. Never in
       a file, so the editor names them but must never offer one to add. A test
       asserts no name is in both this list and cameraKnownEvents().
   cameraKnownEvent(jp)         -> exact lookup, nullptr when unknown
   All three come from ONE store per list in camera_param.cpp, shared with the
   describeCameraId() lookups: there is no second copy to drift.

 Field spec (52 known BCAM fields, in the game's preferred column order)
   struct CameraFieldSpec { name, type, baseDefault, smg2Default, scope, group,
                            label, tooltip }
   cameraFieldSpecs() -> const std::vector<CameraFieldSpec>&
   cameraFieldSpec(name) / cameraFieldSpecForHash(jmapHash) -> const*, or nullptr
   cameraFieldDefault(spec, engineVersion) -> base default unless SMG2 overrides
   cameraFieldApplies(scope, context) -> bool, for UI filtering

 Camtype registry (every CAM_TYPE_* the two games know + 5 aliases)
   struct CameraTypeInfo { id, jpName, label, description, aliasOf,
                           aliasMinVersion, smg1, smg2 }
   cameraTypes() -> all entries (aliases are their own entries)
   cameraTypeInfo(camtype) -> exact lookup, nullptr when unknown
   resolveCameraType(camtype, engineVersion) -> resolves an alias only at/after
   aliasMinVersion (the game gates them by version); unknown ids come back
   verbatim so a modder's custom camtype survives a round trip.

 The table: class CameraParamTable
   CameraParamTable()                       // empty: required columns only
   CameraParamTable(std::vector<std::uint8_t> bytes, io::Endian,
                    std::uint32_t defaultVersion)   // parses a sparse .bcam
   static CameraParamTable create(std::uint32_t defaultVersion)
   struct Camera { std::size_t row; std::string id, camtype; std::uint32_t
                   version; CameraContext context; }
   std::vector<Camera> cameras() const   // identity + context per row
   std::size_t size() const;  bool empty() const
   std::uint32_t engineVersion(std::size_t row) const  // row `version`, else default
   float getFloat(row, field);  std::int32_t getInt(row, field);
   std::string getString(row, field)
       A column the file does not carry falls back to that ROW's engine default;
       an unknown field name falls back to zero/empty.
   bool hasColumn(field) const
       True only when the value really came from the file. THIS is how the UI
       says "engine default" vs "authored value" - never guess by comparing the
       value against the default.
   std::optional<BcsvValue> storedValue(row, field)   // nullopt = no column
   void setFloat/setInt/setString(row, field, value)
       Writing a parameter the sparse file lacked CREATES the column (typed from
       the spec) and fills every OTHER row with its engine default first, so no
       existing camera changes meaning. That is the whole point of the sparse
       model: never "normalise" a file by materialising all 52 columns.
   std::size_t addCamera(id, camtype, version)  // existing columns get engine defaults
   bool removeCamera(row)
   std::uint32_t defaultVersion() const;  BcsvTable& table()  // file-order escape
   std::vector<std::uint8_t> serialize() const

 Pose solving (what the preview drives)
   struct GameCameraPose { math::Vec3f eye, at, up; float fovYRadians;
                           float rollRadians; }   // defaults 45 deg, no roll
   struct CameraPreviewParams {           // one row, flattened, defaults resolved
     std::string id;
     std::string camtype;                 // unresolved, exactly as stored
     math::Vec3f wpoint, axis, up, woffset;
     float angleA{0.0F}; float angleB{0.3F}; float dist{1200.0F}; float roll{0.0F};
     float fovy{45.0F}; float loffset{0.0F}; float loffsetv{0.0F};
     std::uint32_t version{kCameraVersionSmg2};
   }
   CameraPreviewParams cameraPreviewParams(const CameraParamTable&, std::size_t row)
   PoseSupport cameraPoseSupport(std::string_view camtype,
                                 std::uint32_t engineVersion) noexcept
   GameCameraPose solveGameCameraPose(const CameraPreviewParams&,
                                      const math::Vec3f& target,
                                      PoseSupport* support = nullptr) noexcept
       THREE args plus an optional out-pointer. There is no warning-string
       overload: read the PoseSupport out-param (or call cameraPoseSupport) to
       decide what to tell the user. Never fails; degenerate input still returns
       a harmless pose.
       NEW IN THIS SESSION: the inputs are sanitised before solving (finiteOr /
       sanitisePreviewParams, camera_param.cpp just above supportForType). A NaN
       or infinity anywhere in a hand-edited row falls back to that field's
       documented default, and a non-finite `target` becomes the origin, so a
       corrupt file cannot put a non-finite pose into the viewport. Covered by
       testCameraPreviewChain.

 Angle units are NOT uniform (this trips people up):
   fovy   : DEGREES in the file (default 45) - solver multiplies by pi/180.
   roll   : RADIANS (passed through).
   angleA : RADIANS.  angleB: RADIANS.
   CAM_TYPE_POINT_FIX: axis.x/axis.y are DEGREES (the LCP panel edits them as
   degrees) - converted inside that branch only.

 PoseSupport coverage (supportForType, camera_param.cpp:1180) - keep in sync:
   exact     : XZ_PARA, POINT_FIX, EYEPOS_FIX
   spherical : FOLLOW, OBJ_PARALLEL, MTXREG_PARALLEL, CUBE_PLANET, WONDER_PLANET,

5. THE VIEWPORT CAMERA (cpp/include/whitehole/render/camera.hpp)
--------------------------------------------------------------------------------

 ViewportCamera is an ORBIT RIG, not a free camera: {target, yawRadians,
 pitchRadians, distance} plus the newer {fieldOfViewRadians, rollRadians}.
 eye() = target - forward*distance. Everything (view matrix, picking ray, pan,
 worldToScreen, the GL renderer) derives its basis from forward()/up()/right(),
 so one bug in that basis breaks picking, gizmo drags and overlays at once.

 Public surface the feature work touches:
   static constexpr float kFieldOfView = 1.2217305F (70 deg), kNearPlane 10,
   kFarPlane 60000 (legacy fallback), kMinDistance 5, kMaxDistance 150000,
   kMaxDynamicNear 100, kMaxDynamicFar 500000, kMaxPitch 1.55F.
   eye(), viewMatrix(), projectionMatrix(aspect), forward(), up(), right(),
   screenToRay(x,y,w,h), orbit/pan/dolly/dollyTowardCursor, frameTarget,
   lookAt(eye, at, fovRadians=-1, rollRadians=-1), pose(), setPose(pose),
   fly(...), nearPlane(), farPlane(sceneRadius), worldToScreen(...).
   fovRadians/rollRadians < 0 in lookAt() means "leave as is".

 Forward-convention to keep straight (camera.cpp):
   eye() = target + dist * (cos(pitch)*cos(yaw), sin(pitch), cos(pitch)*sin(yaw))
   forward() = normalised (target - eye())
   up()  = (0,+1,0) when cos(pitch) >= 0 else (0,-1,0) - the Java-parity flip;
           pitch is clamped to +/- kMaxPitch (1.55 rad, ~1.2 deg short of
           straight up/down) so that test never fires in normal navigation.
 lookAt() (camera.cpp:180) is the exact inverse, no iteration needed:
   target = at; d = normalise(eye - at); distance = clamp(|eye-at|, kMin, kMax);
   pitch = clamp(asin(d.y), -kMaxPitch, kMaxPitch); yaw = atan2(d.z, d.x).
   A zero-length shot keeps the current angles and just moves the pivot.
   eye() therefore reproduces `eye` exactly EXCEPT within ~1.2 deg of straight
   up/down, where the pitch clamp bites and the eye rides a few units along the
   arc - acceptable for a preview, and worth a tooltip if a tower camera that
   stares at the floor ever matters. fov/roll < 0 means "leave as is".

 THE ORTHOGONAL-ROLL FIX (up(), camera.cpp:25) - do not regress this.
   The no-roll path returns the Java-parity level vector verbatim, so an ordinary
   editor frame is byte-identical to every previous build. Keep it that way:
   `if (rollRadians == 0.0F) return level;` is a deliberate early-out.
   The FIRST roll implementation rotated world Y about the view axis (Rodrigues).
   Wrong: world Y is perpendicular to the view axis only when looking
   horizontally, so at steep pitch the rotated vector is neither unit length nor
   orthogonal to forward, and viewMatrix / screenToRay / worldToScreen stop
   agreeing with each other. The scene renders sheared and clicks land on
   whatever the projection of the broken basis says, not what you see.
   What the code does instead (and what any rewrite must do):
     level   = +/-Y (Java parity)
     along   = dot(level, forward)
     base    = normalise(level - forward * along)   // projected INTO the image plane
     sideways= normalise(cross(forward, base))
     up      = base * cos(roll) + sideways * sin(roll)
   with a degenerate guard (|base| < 1e-6 -> return level: looking exactly along
   the up axis leaves nothing to roll about). base/sideways are orthonormal by
   construction, so up() stays unit and perpendicular to forward for any roll.
   Consequence the next person must respect: roll lives in the BASIS, so every
   consumer must go through up()/right(). Never rebuild a basis from world Y by
   hand at a call site, or rolled previews will pick the wrong object.
   right() = normalise(cross(forward, up())) with its own degenerate fallback
   (cross against +Z, then the hard fallback {1,0,0}).

9. THE TARGET DECISION (decided), PLUS WHAT IS STILL OPEN
--------------------------------------------------------------------------------

 solveGameCameraPose takes `target` = "the point the game tracks (Mario's
 position for c:/s:/g:/o: cameras)". The editor has no running Mario, so the
 panel must supply something. The solver is honest about it: pivot = target +
 woffset, and point-fix style types aim AT target. Whatever you pick moves every
 spherical/exact preview, so it must be visible and user-changeable, never
 hidden magic.

 Options, best first:
   a) Selected object's position, else the nearest StartObj/PlayerStart, else the
      origin - PLUS an explicit "Target" XYZ triplet in the panel the user can
      override. Recommended. SHIPPED, as cameraTargetChoice(): the manual
      override wins, then the selected object, then the first placement row that
      looksLikeStartObject (kind "start", or a name like StartObj/PlayerStart/
      Mario ignoring case), then the origin. The panel ALWAYS shows the resolved
      point and its source, and the last solve's target is cached in
      cameraPreviewTarget.
   b) StartObj/PlayerStart only (PlacementObject rows named like a start).
      Closest to the game, but most stages will resolve to the origin anyway.
   c) Origin always. Simplest, least useful; fine as option (a)'s fallback.
 Whatever you choose, SHOW the resolved target next to the PoseSupport badge. A
 preview that silently frames nothing looks exactly like a broken solver, and
 this feature will get "the preview is wrong" reports that are really "the target
 is the origin" reports.

 PlacementObject comes from state.stage->objects() (iterating example at
 gui_win32.cpp:645; refreshViewport rebuilds ViewportScene from it at :736).
 Resolve names through db/name_table + db/object_db before string matching.

 Still open (do not "fix" these without asking), and none of them is
   documentation debt -- each is either a feature or needs hardware:
    - CREATE ZONE / CREATE GALAXY: CLOSED, and no longer a camera concern. The
      builder, the template loader and the GUI's layer picker all shipped
      (sections 15 and 16 item 2). What remains is hardware verification, tracked
      in section 16 item 1 -- not here.
   - The cutscene/scenario-starter types are now AUTHORABLE, but a row added that
     way will usually land on a camtype the solver reports PoseSupport::none for
     (CAM_TYPE_ANIM / RAIL_DEMO are keyframed over time in game). The badge says
     so honestly; a time slider + key sampling is still its own feature.
   - Per-zone tables: StageArchive loads ONE CameraParam.bcam per open map file,
     so "zone" is currently "the map file you opened". A per-zone picker implies a
     StageArchive change first.
   - Screen-region columns exist in the BCAM spec but are NOT modelled in
     CameraPreviewParams, so the preview does not crop to the game's screen
     rectangle. Deliberate: the decompiled translators apply it after the pose.
     If someone adds it, it belongs in the projection, not in eye/at.
   - SMG1 rows default several fields differently; hasColumn() is the only
     trustworthy answer. Never render a defaulted 0 as if it were authored.
   - `roll` is passed straight through as radians. Whether the game treats it as
     camera-local or screen-space was inferred from the translators, not verified

10. TOOLING TRAPS THAT COST REAL TIME (read before typing a command)
--------------------------------------------------------------------------------

 - This shell is Windows PowerShell. `&&` is NOT a statement separator - use ';'
   or separate calls. Quote paths that contain spaces. Do not wrap a command in
   another powershell.exe -Command.
 - git is NOT on PATH here. Call it as:
       & 'C:\Program Files\Git\cmd\git.exe' --no-pager <args>
   Always --no-pager, or the call hangs on a pager.
 - Build with out-of-tree directories and the recipe in section 2 (never a
   checked-in tree): devkitPro's make is gone, cmake uses Ninja instead, and a
   stale in-repo build dir would dirty hundreds of tracked files on every
   compile.
 - MSVC needs the machine's vswhere on PATH before vcvars: older sessions had a
   working VS2022, but this machine's VS2022 lost vcvarsall.bat AND the VS
   Installer (no vswhere), so cmake reports "could not find any instance of
   Visual Studio". What works is VS2026's vcvars64.bat plus
   C:\Program Files (x86)\Microsoft Visual Studio\Installer on PATH.
 - A single shell command is killed after ~30 seconds, INCLUDING its output, so
   a first full build never finishes in one call. Run the build detached via
   Start-Process (a .cmd that redirects to a log file) and poll the log. Do not
   fight it by repeating foreground builds: each kill restarts ninja's in-flight
   compiles and truncates .ninja_log ("premature end of file; recovering"),
   which then rebuilds the same files over and over.
 - Do not wrap a PowerShell command that needs cmd separators in another
   powershell.exe -Command: PowerShell 5.1 has no && operator, and cmd /c with
   embedded quotes inside a PowerShell string mangles the call. For batch
   helpers, write a .cmd file with the editor tool (with cmd-style quoting),
   not by assembling quoted strings in PowerShell.
 - Do not rewrite source files with PowerShell Set-Content/Out-File - it can
   change encoding and line endings. Use the editor tool.
 - The edit tool is chunk-limited (~6k chars per call). For a long document,
   several inserts at known line numbers beat one big write - and re-check the
   line count between inserts, because every insert shifts all later numbers.
 - The file on disk is UTF-8 (the /utf-8 compile flag is there for a reason), but
   PowerShell prints the Japanese camtype jpNames as mojibake. That is a console
   rendering artefact, NOT corruption - verify with the editor tool before
   "fixing" it. This exact false alarm already happened once here.
  - A carried-over context summary is a SUMMARY, not ground truth. When it
    disagrees with the header, the header wins, and that is why section 4 exists.

  - AN OPEN std::ofstream IS A LOCKED FILE, AND MINGW WILL NOT TELL YOU. Scope

13. THE SCENARIO TABLES (cpp/include/whitehole/smg/scenario_model.hpp)
================================================================================

  GalaxyArchive used to read ZoneList.bcsv, keep only a vector of zone NAMES, and
  throw the table away, while ScenarioData.bcsv was loaded and never displayed by
  anyone. Both are now kept as tables (zoneList()/scenarioData()/galaxyInfo(), plus
  non-const overloads) with dirty() and save() on top.

  FORMAT FACTS - read from the game's OWN code, not guessed:
   Sources, in order of authority: StageHelper.java:1042-1061
   (populateScenarioFieldsScenarioData, which WRITES the columns and states their
   types), GalaxyArchive.java:60-71 (getActiveLayerNames), and the decompiled
   ScenarioData.cpp in GalaxyTools/Garigari + Petari. Scenaristar was the FEATURE
   reference; none of its code was used.
   * Column order/types: ScenarioNo(int) ScenarioName(str) PowerStarId(int)
     AppearPowerStarObj(str) Comet(str) LuigiModeTimer(int), then for SMG2 ONLY
     PowerStarType(str) CometLimitTimer(int), then ONE INTEGER COLUMN PER ZONE.
     SMG1 replaces the SMG2 pair with an integer IsHidden.
   * `Comet` is a STRING holding the comet kind ("Dark"), not a flag.
   * ScenarioNo is the game's 1-based id and is what it looks a scenario up by --
     NOT the row order.
   * PowerStarType is compared as a string; the game excludes Hidden and Green from
     the "normal star" count (getPowerStarNum vs getNormalPowerStarNum).
   * PowerStarId is ONE INTEGER, NOT A BITMASK of the scenario's declared stars.
     Scenaristar's ScenarioData.cs writes the accessor as (PowerStarID & (1 <<
     StarID)) and tags that line "//TODO: TEST THIS". The game's own
     ScenarioData::getPowerStarNum reads a single u32 and only tests it for
     non-zero, and getScenarioNum does the same for IsHidden -- so "awards a
     star" is exactly `id != 0`. Someone porting from Scenaristar will be tempted
     to "fix" this toward the bitmask. Don't: testScenarioEditing pins
     setPowerStar(4) == 4 and awardsStar() on and off so that regression fails the
     suite instead of reaching a galaxy.

   * THE LAYER RULE: every per-zone column IS that zone's layer mask, read RAW.
     Bit 0 = LayerA ... bit 15 = LayerP; "Common" is always on and owns no bit.
     Java parity, verbatim: layerList.add("Common"); for (i<16) if (mask & (1<<i))
     add("Layer" + 'A'+i). The bundled template proves it: its RedBlueExGalaxy
     column holds 1/2/4 for the three missions that use LayerA/LayerB/LayerC.
   * The game's getValueU32() MULTIPLIES the stored mask by two before its caller
     uses it. That multiply belongs to the CALLER. Do not fold it into layerMask()
     or every bit lands one position off.

  THREE TRAPS THAT COST REAL TIME HERE - do not repeat them:
   1. fieldHash() IS NOT jmapHash(). `whitehole-pro-console hash ScenarioNo`
      prints JMap 0x7DAF4852, but BcsvTable writes with fieldHash() = 0xED08B591.
      Hardcoding the printed value made isScenarioOwnHash() never match, so the
      copy-a-scenario pass treated ScenarioNo as a layer column and overwrote the
      copy's id with the source's -- silently, with no error. Compute the hashes
      with fieldHash() at runtime, exactly as the writer does.
   2. A BCSV row reference dies the moment a column is appended. ensureField()
      rewrites every stored row, so holding `BcsvRow& cells = rows()[row]` across
      one is a dangling reference. Address rows by index and re-fetch.
   3. `fields()` is the NON-const accessor and clears the cached hash index, so a
      BcsvField& held across a write reads stale values. Snapshot the hashes into a
      local vector before the write loop.

  What save() guarantees: an UNTOUCHED galaxy is not rewritten at all (not-dirty
  and byte-identical are different claims, and only the first is guaranteed without
  writing); GalaxyInfo.bcsv is never created for a galaxy that shipped without one.
  testScenarioModel / testScenarioEditing / testGalaxyScenarioSave pin all of it,
  including that a layer edit and its exact inverse are byte-exact.

  THE PANEL (gui_win32.cpp), and the two rules that keep it honest:
   * TWO DOCUMENTS, TWO STACKS. EditorState holds `galaxy` (a GalaxyArchive BY
     VALUE) beside `stage`, plus `scenarioUndoStack` beside `undoStack`. Ctrl+Z
     goes to the galaxy's stack when a mission is selected, else the zone's
     (scenarioUndoActive()), and the Scenarios panel prints its own undo label so
     the seam is never a mystery. selectZone() clears the zone stack, which is
     exactly why they cannot be one stack.
   * GalaxyArchive borrows the workspace filesystem OUT of state.game, so
     resetGalaxy() runs at the top of openMapImpl, openGameImpl and selectGalaxy.
     Miss one and it is a dangling pointer, not a compile error -- this is the
     single most dangerous line in the feature.
   * The model is rebuilt from the archive EVERY FRAME. These tables are a few
     hundred bytes, and it means the panel cannot display something an undo has
     already replaced. Inside a commit lambda the model is rebuilt again from the
     tables the lambda is handed, never captured.
   * Common is drawn as a LOCKED column in the layer matrix: it owns no bit in the
     file (scenarioLayerBit("Common") == -1), so offering it as an editable
     checkbox would be a lie the save would not honour.
   * An SMG1 galaxy has no PowerStarType column. The panel says so instead of
     offering a picker that would ADD a column the game never asked for.

14. CREATING ARCHIVES FROM NOTHING (cpp/include/whitehole/io/rarc.hpp)
================================================================================

  Until d51b851, every RarcArchive entry point PARSED bytes that already existed.
  That is a hard floor on what the app can do: a zone cannot be created, because
  there is no archive to write into before it holds a single file.

  RarcArchive::create(rootName, metadata = 0) returns an empty archive with a
  root node and no entries; createDirectory() and the existing insert() fill it
  like any other archive. It reuses the EXISTING serializer, which already built
  its whole node/entry/string table from rootName_ + entries_ -- so there is no
  second writer to keep in step with the first.

  THREE INVARIANTS, all found by the test, all invisible until violated:

   1. THE ROOT NODE IS IMPLICIT. parse() builds it without ever putting it in
      entries_, and serialize() re-creates it from rootName_. So find() alone can
      NEVER resolve it, and any code that validates a parent with find() rejects
      the first directory a new archive needs. Parent checks go through the
      file-local hasDirectory(), which also matches rootName_ directly.

   2. ENTRY PATHS ARE STORED ROOT-PREFIXED, WITH THEIR ORIGINAL CASING
      ("Stage/jmp", not "/stage/jmp"). serialize() looks each entry's parent up
      in a map keyed by rootName_ and by the paths earlier entries were stored
      under -- an exact, case-sensitive lookup. Storing the normalized form from
      normalizePath() (which lowercases) fails with "directory has no serialized
      parent" on an archive that is perfectly well formed. insert() already did
      this correctly; createDirectory() has to match it.

   3. APPLY THE ROOT PREFIX BEFORE CHECKING THE PARENT. "/jmp" is a TOP-LEVEL
      directory, so its parent IS the root. Checking first sees an empty parent
      and throws "cannot create the root directory".

  WHAT IS PROVEN, AND WHAT IS NOT: the test builds an archive, writes it,
  re-parses it, and reopens it through StageArchive::openMapFile -- the same
  loader the editor uses for every zone -- then reads a placement object out of
  it. That establishes an archive built this way is indistinguishable from a
  parsed one to all of Whitehole Pro. It does NOT establish that a retail copy of
  SMG1/SMG2 would accept it: no game was run. Treat "the game reads this" as
  unverified until someone opens a created zone on hardware.

  createDirectory() is idempotent (creating an existing directory returns quietly,
  because the zone builder asks for the same folder from more than one layer) and
  refuses a missing parent. create() refuses an unsafe root name. Temporary names
  for saves are unique per writer -- see section 10 for why a fixed ".tmp" is a
  race.

  STILL TO BUILD ON THIS: roadmap item 5's create zone / create galaxy, the
  template loader (data/templates/*.json ships with the repo and NOTHING in the
  C++ reads it yet), and the GUI's layer picker. Derive each layer's JMP schemas
  from the shipped template archive rather than transcribing Java's thirteen
  populateJMapFields* functions -- SMG2StandardZoneMap.arc is already a correct
  bare zone with the exact layout and the one StartInfo row Java adds.

   [done]  CREATE ZONE / CREATE GALAXY, and the template loader. The builder

15. CREATING ZONES AND GALAXIES (cpp/include/whitehole/smg/stage_builder.hpp)
================================================================================

  THE DESIGN DECISION, because it is the whole reason this was tractable:
  Java builds every JMap file by hand through thirteen populateJMapFields*
  functions -- ObjInfo alone is 38 fields, and a wrong field is a zone the game
  rejects. But every one of those field lists is ALREADY in the template
  archives shipped in data/templates: a template is a real game file with the
  right schema and no rows. So the builder COPIES the schema and transcribes
  nothing, and the scenario side asks ScenarioModel, which already owns the
  columns and the SMG1/SMG2 split. Roughly 400 lines of hand-transcribed
  guessing became a loop over a file the game itself produced.

  That is also why a template is REQUIRED even for a "bare minimum" zone:
  without a real game file there is no trustworthy schema, and the builder
  refuses rather than inventing one. bareMinimumMapArchive() is the bundled
  per-game bare zone (SMG2StandardZoneMap.arc / SMG1OneStarGalaxy.arc).

  THE FOUR BUGS, all found by the test, all silent except the first:

   1. createDirectory()'s idempotence check used find(), which falls back to a
      bare-filename and path-suffix match. Asking whether ".../MapParts/Common"
      exists was answered by the FILE ".../MapParts/Common/MapPartsInfo" -- a
      suffix match, and not a directory. The per-layer directory was skipped, and
      every file in it then failed to serialize for having no parent.

   2. insert() had the SAME problem, and far worse. Every layer's tables have the
      SAME file names (Common/StartInfo, LayerA/StartInfo, ...), so inserting
      LayerA's table found Common's and REPLACED it. The archive looked
      complete -- every layer directory was present -- while every non-Common
      layer silently held no tables at all. insert() now uses findExact(); the
      loose fallback is right for a human reading a path and catastrophic for a
      writer.

   3. ensureScenarioColumns() unconditionally created PowerStarType and
      CometLimitTimer, which are SMG2-ONLY. Adding a mission to an SMG1 galaxy
      would have put columns in the file the game has never seen -- exactly the
      mistake the Scenarios panel refuses to make with its star-type picker. It
      now reads the game's own SMG1 marker (IsHidden) to decide.

   4. A fresh galaxy's first mission awarded NO star, because addScenario()
      deliberately leaves a new mission empty -- right for the panel's "add a
      mission", wrong for a galaxy's FIRST, which would open handing out no
      stars at all. Java's own starter row sets PowerStarId = ScenarioNo.

  LAYOUT FACTS THAT ARE EASY TO GET WRONG, all from StageHelper:
   * SMG1 lowercases EVERY path: /stage/jmp/placement/common. The root of an SMG1
     scenario archive is lowercased too, but the FILE name is not.
   * SoundInfo and ChildObjInfo are SMG1-ONLY; creating them for SMG2 adds files
     the game does not expect. (This is why stageLayeredTables() is shared with
     the loader -- see section 11.)
   * GalaxyInfo is SMG2-ONLY. Its absence is MEANINGFUL: the Scenarios panel
     reads an absent PowerStarType as "this galaxy records no star type".
   * SMG1 zones are FLAT (/StageData/<zone>.arc); SMG2 zones get a folder.

  WHAT IS PROVEN, AND WHAT IS NOT: a created zone reopens through
  StageArchive::open (the loader the editor itself uses) with its spawn point and
  its tables, and a created galaxy reopens through GalaxyArchive with its map
  zone leading the editable list. Both games are covered, and the template is
  byte-identical afterwards. This does NOT establish that a retail SMG1/SMG2
  accepts a created zone: no game has been run against it. Treat "the game reads
  this" as unverified until someone opens a created zone on hardware.

  LANDED" block below for what shipped.

       * canonicalLayerName() is applied INSIDE rebuild(). An SMG1 archive spells
         its layer directories lowercase and scenarioLayerBit() is CASE-SENSITIVE,
         so a filter on the raw string would hide nothing on SMG1 and everything
         on SMG2, with no error anywhere. Both spellings are pinned by test.

     Tests: testLayerFilter (the value type), testLayerFilteredScene (the wiring
     -- index stability, unpickable hidden objects, the marquee, frame-all with
     its all-hidden fallback, overlays, the SMG1 case, the mask round trip) and
     testSnapSkipsHiddenLayers. Registered next to testLayerFilter in main().

     STILL UNVERIFIED, like everything else here: compile-verified and unit
     tested, but no human has clicked a layer checkbox. See section 16 item 1.

  4. ANIMATIONS (roadmap 2). Spin platforms, doors, live stars. The largest
     single feature: it needs BCK/BPK/BRK/BTK parsers AND a timeline UI AND a
     preview. Everything above is smaller than this.

  5. KCL COLLISION RENDERING (roadmap 1). [DONE] Collision-aware picking is the
      single change that would most improve day-to-day editing, because clicking
      through geometry correctly is what an editor is judged on. Snapping was
      already there; this added the PICKING half and the overlay.
THE DECISION IS PURE AND TESTED, in render/surface_snap, deliberately away
      from the Win32 path that cannot be unit-tested:
        rayIntersectsCollision(origin, dir, triangles, maxDistance) -> CollisionHit
          {distance, point, KCL face normal, sourceIndex}. Normalises the
          direction, so a caller passing a non-unit vector gets a DISTANCE back
          rather than a ray parameter -- otherwise the two get compared wrongly.
        collisionOccludes(hit, candidateDistance) -> should reject
          Shaped as "reject" not "accept" on purpose: with no collision on the ray
          it returns false, which IS the pre-existing behaviour, so the feature
          degrades to what came before instead of failing open.

      THREE THINGS THAT WOULD HAVE LOOKED LIKE FEATURES AND WERE BUGS:
        * WITHOUT the on-surface tolerance, every click on a modelled object
          rejects itself against its own collision, and in a collision zone
          NOTHING is selectable. That would have read as a catastrophic
          regression rather than an improvement. kOnSurfaceTolerance = 0.05.
        * The forgiving pick FALLBACK (no box under the cursor, one picked by 10px
          proximity) usually has no ray hit, so no distance and no occlusion. That
          is deliberate: a proximity pick is a "you probably meant this" gesture.
        * Zone-level KCL with no placement owner selects NOTHING rather than
          something misleading.

      Clicking a wall selects the WALL (sourceIndex names its owner), which is the
      whole point of carrying sourceIndex through from parseKclTriangles.
      WHY the distance is re-derived in pickAt rather than returned by
      pickForgiving: that returns a box INDEX, the rule needs a DISTANCE, and
      rayIntersectsBox() is already a free function over the same box -- so one
      more ray on a discrete click costs nothing, and changing that signature
      would reach the camera, the gizmo and the marquee for no user-visible gain.

      THE OVERLAY: View > Overlays > Collision, off by default. It is NOT an
      OverlayFlags family -- the soup lives on ViewportWindow and is replaced once
      per zone load, whereas OverlayFlags drives ViewportScene::rebuild(), so
      coupling them would force a full scene rebuild on every KCL load. Built
      LAZILY on the off->on edge and cached, because a dense zone is ~200k
      triangles and per-frame rebuilds would cost more than the rest of the
      overlay together. The wireframe is WELDED (collisionSegmentsFor(), tested):
      a KCL is a closed mesh, so naive 3-per-triangle output draws every interior
      edge and turns a planet's hull into a thicket. std::hash is not specialised
      for std::pair before C++26, so the edge set needs its own hash -- MSVC
      rejects the default outright and GCC only fails when it is used.

      STILL UNVERIFIED, and it needs a human: clicking through a wall is
      unit-tested at the decision level, but the wiring is only compile-verified.

  6. BCSV SPREADSHEET (roadmap 4). Lower value than it looks: the panels now
     cover the fields people actually edit. The real win is BULK editing, not
     visibility.

  7. Model/texture browser, specialized renderers (star trajectories, world-map
     links), cross-platform GUI. All real, all later.

  Deliberately NOT on this list, from section 9: the cutscene time slider, the
  screen-region projection, per-zone camera tables. Each is either its own
  feature or needs hardware; section 9 says why, and that reasoning still holds.

17. SUGGESTIONS (opinion, not plan -- none of this is promised work)
================================================================================

  Things I noticed while working that would pay back more than the feature they
  came from. Recorded so the next session can pick them up if they agree.

  STATUS: SEVEN of these are DONE and carry a [DONE] marker with what they found --
  the findExact() convention, temp-file naming, --dry-run, the round-trip property
  tests, the shipped-template check, the API holes, and "document NOT UNDOABLE in
  the UI". Two are still open: the "verify against retail" checklist, and the
  find() lint (the convention is written down and pinned by a test, but nothing
  mechanically stops a new writer from calling find()).

  WHAT THE DONE ONES ACTUALLY FOUND, because it is the pattern worth carrying
  forward: five of them were bugs NO TEST WOULD HAVE CAUGHT, because the wrong
  answer was silent --
    * scenarioLayerBit() returned -1 for EVERY object in EVERY SMG1 zone;
    * "Layer" + char was POINTER ARITHMETIC, reading adjacent string-literal
      memory, clean under /W4 AND -Wconversion;
    * the object-database download deleted its destination BEFORE renaming it, so
      a failed rename left the modder with nothing;
    * without the on-surface tolerance, every click on a modelled object would
      have rejected itself against its own collision, making collision zones
      entirely unselectable -- indistinguishable from "the feature broke the
      editor";
    * and boxes_[i].objectIndex == i is a coupling nothing declares, so the
      obvious layer-filter implementation would have made clicking object 5
      select object 4.
  In this codebase the dangerous changes are the ones that compile clean and look
  right. Budget for that.

  * A "VERIFY AGAINST RETAIL" CHECKLIST for every format change. The one test
    that would have caught section 15's worst bug -- a layer silently holding no
    tables -- is opening the result in a real game, and that is not automatable
    here. Make it a documented step BEFORE the code lands, not something the
    author remembers afterwards. It is the single highest-value process change
    available to this repo.

  * GUARD AGAINST THE find() CLASS OF BUG. Section 15 lost data TWICE to a
    lookup that is deliberately loose (it falls back to bare-filename and
    suffix matching, which is right for a human reading a path and wrong for
    anything writing). The cheap systemic fix is a convention or a lint: write
    paths use findExact() and nothing else. It bit twice in one feature and will
    bite again.

  * MORE ROUND-TRIP PROPERTY TESTS. [DONE, and it found two things]
    testRarcRoundTripProperties + testBcsvRoundTripProperties now build across
    shapes (nested dirs, mixed casing, empty files, zero-row tables), serialize,
    re-parse and compare. THREE FACTS they established, each of which cost a
    failed run to learn:

      1. A BUILT-FROM-NOTHING ARCHIVE IS NOT BYTE-STABLE ACROSS A RE-PARSE, and
         does not need to be. parse() rebuilds entries_ in node-tree order while
         a builder appends directories and files as it goes, and serialize()
         lays out the string table by walking entries_ -- so identical TREES give
         different bytes. The law in section 3 is about an untouched PARSED file
         re-saving identically, and THAT is asserted (and passes). Do not "fix"
         the built case by trying to make entry order canonical.
      2. CASE ON A DIRECTORY PATH BREAKS SERIALIZATION. insert() resolves parents
         case-INSENSITIVELY, so writing "jmp/placement/common/X" under a
         directory created as "jmp/Placement/Common" is accepted and then fails
         at save with "RARC file has no serialized parent", because serialize()'s
         parent map is keyed by the exact stored paths. That is section 14
         invariant 2, and nothing in the code stops you from walking into it.
         Mixed casing is safe on FILE NAMES only.
      3. A DEFAULT-CONSTRUCTED BcsvTable IS BIG-ENDIAN and there is no public way
         to build a little-endian one -- only to parse one. Iterating both
         endiannesses when constructing tables from scratch means writing big
         bytes and re-parsing them claiming to be little. testBcsvEndianness
         covers the little path.

  * A --dry-run FOR THE CREATE COMMANDS. [DONE] `zone create --dry-run` and
    `galaxy create --dry-run` print every file that would be written and stop.
    It is a PLAN/APPLY SPLIT, not a flag that suppresses the writes:
    planStageZone()/planGalaxy() in stage_builder return a StageCreatePlan
    (mapPath, resolved layers, every JMap path, plus scenarioPath + extraZones
    for a galaxy), and create* BUILD THEIR PLAN THROUGH THEM and then apply it.
    That is the part that matters -- a bool flag would still build every archive
    and every BCSV, so the "preview" would cost what the real thing costs and
    could still fail on the thing it promised to preview, and the two file lists
    could drift. Normalizing the layers also became a public
    normalizeStageLayers(), because a layer picker must show the resolved truth
    and reject "LayerZ" rather than silently drop it.
    One honest limit, documented in the header: a plan CANNOT know whether the
    zone already exists, because that is a fact about the destination and
    planning never looks at it. The CLI re-checks it after planning, and
    testStageCreatePlans pins plan == what create actually wrote.

  * DOCUMENT "NOT UNDOABLE" IN THE UI, NOT ONLY HERE. [DONE] The confirm step of
    Project > Create now prints it in the Scenarios panel's own TextDisabled voice.
    cannot be undone by the snapshot model. The gap section 15 records is now
    closed on screen rather than only here.

  * UNIFY TEMP-FILE NAMING. [DONE, and the blueprint's version of this was
    WRONG] It said writeFile() had been fixed but "the builder and the CLI do
    not create temporaries". That is not what the code does: DirectoryFilesystem
    ::write() already delegates to writeFile(), so the builder and CLI were safe
    all along. Auditing every std::ofstream instead found THREE real bypasses,
    all in the app layer, none covered by testWriteFileLeavesNoTemporaries:
      * object_db_update.cpp staged into a FIXED ".download" name -- the exact
        race writeFile() was fixed for -- and then remove()d the destination
        BEFORE renaming, so a failed rename (AV scanner, a second instance) left
        the modder with NO database instead of the old one. Now one writeFile()
        call: fixed race, closed data-loss window, .bak for free.
      * custom_obj_db.cpp truncated straight onto the live file. That file is the
        modder's own object registry -- work that exists nowhere else -- so an
        interrupted write destroyed real authoring.
      * settings.cpp had the same shape (low stakes, same hole).
    temporaryPathFor() is now PUBLIC in binary_file.hpp so a caller that cannot
    use writeFile() cannot invent a second naming scheme that drifts.

  * A TEST THAT THE TEMPLATES ON DISK STILL PARSE. [DONE] testShippedTemplatesParse
    walks data/templates/*.json through all four (game, galaxy/zone) filters and
    asserts each map archive EXISTS, OPENS as a RARC (not merely non-empty), and
    carries at least one /jmp/ table -- plus that every declared ScenarioFile
    exists and opens, and that both games' bare-minimum archives open. The gap it
    fills over testStageTemplates is specific: that test only checked mapArchive()
    returning non-empty bytes, and only for the SMG2 GALAXY templates. SMG1's
    galaxies, both zone templates, every ScenarioFile, and "parses" as opposed to
    "is not empty" were all unverified. Asserts a floor of 5 templates rather
    than an exact list, so adding one is not a failure while deleting one is.

  * CLOSE THE TWO UNDOCUMENTED API HOLES. [DONE] scenarioArchivePath() replaces
    zoneScenarioPath()/galaxyScenarioPath(): one function, no gameType parameter
    that was accepted and discarded, documented as game-independent on purpose.
    stage_templates.hpp is still not mentioned above.
