3. CODE CONVENTIONS (enforced by review, not by a linter)
--------------------------------------------------------------------------------

 - C++20, no compiler extensions. `[[nodiscard]]` on anything that returns a
   value the caller must not drop; `noexcept` where it genuinely cannot throw
   (the camera math is all noexcept).
 - Comments are the deliverable, not filler. Every non-obvious decision gets a
   comment that says WHY, in plain English, usually 2-5 lines above the code.
   The camera code is commented at essay length because it is all reverse
   engineered; keep that tone.
 - ASCII only in sources: use "--" and "==" instead of em/en dashes. The header
   jpName strings are the one exception (they are game data).
 - Namespace layout mirrors the folder: whitehole::math / io / smg / render /
   edit / db / app.
 - Style of a feature here: small typed value struct + free functions over a
   table class (see CameraParamTable + cameraPreviewParams + solveGameCameraPose)
   rather than a god-object. Do not add virtual inheritance.
 - Never break byte-exact round trips: a table that was not edited must save
   back identical (BCSV writer may only append alignment padding). Same rule for
   RARC. If your change makes an untouched file differ, that is a bug.
 - The GUI is immediate-mode ImGui inside a Win32 shell; state lives in
   `struct EditorState` (gui_win32.cpp:131), panels are free functions taking
   `EditorState&` (e.g. drawObjectsPanel at gui_win32.cpp:2077). The editor lives
   in runGui(executable, initialFile) (gui_win32.cpp:4835) - its `EditorState
   state;` is at :4947 and the per-frame work (layout pass at :5121) follows.
   Mutations go through markDirty() (gui_win32.cpp:1263) + refreshViewport()
   (gui_win32.cpp:715) + the UndoStack.
   User-visible errors go through pushToast(state, text, error)
   (gui_win32.cpp:590). Viewport child window placement: syncViewportChild
   (gui_win32.cpp:3300). Fonts/theme apply once at boot right after
   ImGui_ImplWin32_GetDpiScaleForHwnd, with a guard that clamps implausible DPI
   readings to 1.0 - do not load fonts before that.

5. THE VIEWPORT CAMERA (cpp/include/whitehole/render/camera.hpp)
--------------------------------------------------------------------------------

 ViewportCamera is an ORBIT RIG, not a free camera: {target, yawRadians,
 pitchRadians, distance} plus the newer {fieldOfViewRadians, rollRadians}.
 eye() = target - forward*distance. Everything (view matrix, picking ray, pan,
 worldToScreen, the GL renderer) derives its basis from forward()/up()/right(),
 so one bug in that basis breaks picking, gizmo drags and overlays at once.

 Public surface the feature work touches:
   static constexpr float kFieldOfView = 1.2217305F (70 deg), kNearPlane 10,
   kFarPlane 60000 (legacy fallback), kMinDistance 5, kMaxDistance 150000,
   kMaxDynamicNear 100, kMaxDynamicFar 500000, kMaxPitch 1.55F.
   eye(), viewMatrix(), projectionMatrix(aspect), forward(), up(), right(),
   screenToRay(x,y,w,h), orbit/pan/dolly/dollyTowardCursor, frameTarget,
   lookAt(eye, at, fovRadians=-1, rollRadians=-1), pose(), setPose(pose),
   fly(...), nearPlane(), farPlane(sceneRadius), worldToScreen(...).
   fovRadians/rollRadians < 0 in lookAt() means "leave as is".

 Forward-convention to keep straight (camera.cpp):
   eye() = target + dist * (cos(pitch)*cos(yaw), sin(pitch), cos(pitch)*sin(yaw))
   forward() = normalised (target - eye())
   up()  = (0,+1,0) when cos(pitch) >= 0 else (0,-1,0) - the Java-parity flip;
           pitch is clamped to +/- kMaxPitch (1.55 rad, ~1.2 deg short of
           straight up/down) so that test never fires in normal navigation.
 lookAt() (camera.cpp:180) is the exact inverse, no iteration needed:
   target = at; d = normalise(eye - at); distance = clamp(|eye-at|, kMin, kMax);
   pitch = clamp(asin(d.y), -kMaxPitch, kMaxPitch); yaw = atan2(d.z, d.x).
   A zero-length shot keeps the current angles and just moves the pivot.
   eye() therefore reproduces `eye` exactly EXCEPT within ~1.2 deg of straight
   up/down, where the pitch clamp bites and the eye rides a few units along the
   arc - acceptable for a preview, and worth a tooltip if a tower camera that
   stares at the floor ever matters. fov/roll < 0 means "leave as is".

 THE ORTHOGONAL-ROLL FIX (up(), camera.cpp:25) - do not regress this.
   The no-roll path returns the Java-parity level vector verbatim, so an ordinary
   editor frame is byte-identical to every previous build. Keep it that way:
   `if (rollRadians == 0.0F) return level;` is a deliberate early-out.
   The FIRST roll implementation rotated world Y about the view axis (Rodrigues).
   Wrong: world Y is perpendicular to the view axis only when looking
   horizontally, so at steep pitch the rotated vector is neither unit length nor
   orthogonal to forward, and viewMatrix / screenToRay / worldToScreen stop
   agreeing with each other. The scene renders sheared and clicks land on
   whatever the projection of the broken basis says, not what you see.
   What the code does instead (and what any rewrite must do):
     level   = +/-Y (Java parity)
     along   = dot(level, forward)
     base    = normalise(level - forward * along)   // projected INTO the image plane
     sideways= normalise(cross(forward, base))
     up      = base * cos(roll) + sideways * sin(roll)
   with a degenerate guard (|base| < 1e-6 -> return level: looking exactly along
   the up axis leaves nothing to roll about). base/sideways are orthonormal by
   construction, so up() stays unit and perpendicular to forward for any roll.
   Consequence the next person must respect: roll lives in the BASIS, so every
   consumer must go through up()/right(). Never rebuild a basis from world Y by
   hand at a call site, or rolled previews will pick the wrong object.
   right() = normalise(cross(forward, up())) with its own degenerate fallback
   (cross against +Z, then the hard fallback {1,0,0}).

6. THE CAMERA PREVIEW LIFECYCLE (cpp/src/render/viewport_win32.cpp)
--------------------------------------------------------------------------------

 Declared in viewport_win32.hpp:221-245.

 Implementation facts (viewport_win32.cpp:1139-1170):
   begin: on the FIRST call only, saves camera_.pose() and
          camera_.fieldOfViewRadians. Roll is not saved - navigation never sets
          it, so 0 is always the editing value. Cancels tween_ (a running
          smooth-focus tween would fight the pose and then dump the camera
          somewhere random when the preview ended).
   update: camera_.lookAt(eye, at, fov, roll) + invalidate().
   end: restores the saved pose + FOV, forces roll 0, cancels the tween.
   Input swallow (handleMessage, viewport_win32.cpp:1193): while a preview is
   active, ANY of WM_LBUTTONDOWN / WM_LBUTTONDBLCLK / WM_MBUTTONDOWN /
   WM_RBUTTONDOWN / WM_MOUSEWHEEL / WM_MOUSEHWHEEL / WM_KEYDOWN / WM_SYSKEYDOWN /
   WM_CHAR ends the preview, fires onCameraPreviewExit_, and returns 0 - the
   gesture is swallowed so one click does not both exit and orbit/select.
   WM_PAINT / WM_SIZE / WM_ERASEBKGND / focus still run, so the previewed frame
   keeps redrawing while the shell moves. pollInput (fly keys, viewport_win32.cpp
   :2271) is guarded the same way; flycam drag is not a way out.
   Consequence for the GUI: the "Previewing" checkbox MUST be driven by
   setOnCameraPreviewExit (the viewport tells you when it self-exits), not by
   trusting your own toggle. DONE: the single hook in initViewport now clears
   cameraPreviewOpen and cameraPreviewRow and then pushes the toast "Camera
   preview ended: editor navigation is back." Do not register a second
   callback: the setter stores ONE std::function, so a second call silently
   replaces the panel's state clearing with the toast again.

 Design intent, in case someone is tempted to "improve" it: the preview reuses
 the ONE editor camera rather than introducing a second camera or a second
 frustum, so every downstream consumer (labels, gizmo, overlays, picking, the
 reversed-Z projection) keeps working with zero changes. A second camera would
 have needed the same roll fix in five call sites.

 8.0 THE FICTION THAT WAS REVERTED - do not repeat it. The draft assumed:
       game::CameraRecord with eyePoint/focusPoint/focusOffset/rotX/rotY/rotZ/
         nearPlane/farPlane/range/distance/priority/unknownIntA/screenL/R/T/B
       cameraPreviewParams(table, row) -> that struct

       cameraPoseSupport(params, pose)

     ALL WRONG. The real names are in section 4. The real struct has
     wpoint/axis/up/woffset/angleA/angleB/dist/roll/fovy/loffset/loffsetv.
     There are no near/far/priority/screen-region fields in CameraPreviewParams

 8.1 WHERE THE DATA LIVES
     auto& table = state.stage->cameraParams();          // StageArchive

 8.2 THE CHAIN (this is the entire feature, honestly)
     `state.viewport` is a VALUE MEMBER of EditorState
     (`render::ViewportWindow viewport;`, gui_win32.cpp:166) - it is NOT a
     pointer/unique_ptr, so use `state.viewport.foo()`, never `->`. It is only
     usable once `state.viewportReady` is true (see the guard at :716).

     smg::CameraPreviewParams p = smg::cameraPreviewParams(table, cam.row);
     const math::Vec3f target = cameraTargetChoice(state).point;   // section 9, decided
     smg::PoseSupport support = smg::PoseSupport::none;
     const smg::GameCameraPose pose = smg::solveGameCameraPose(p, target, &support);
     render::ViewportWindow::CameraPreviewPose vp;
     vp.eye         = pose.eye;
     vp.at          = pose.at;
     vp.fovRadians  = pose.fovYRadians;
     vp.rollRadians = pose.rollRadians;
     state.viewport.beginCameraPreview(vp);   // or updateCameraPreview while live
     pose.up is intentionally ignored: the viewport derives the basis from
     eye/at plus roll (section 5). Do not add an `up` to CameraPreviewPose; if
     you think you need it, the roll projection in up() is what you should fix.

 8.3 STATE (kept in EditorState, near the other viewport state)
     bool     cameraPreviewOpen{false};     // the "Previewing" toggle
     std::optional<std::size_t> cameraPreviewRow;   // which row owns the preview
     math::Vec3f cameraPreviewTarget{};     // the point the last solve was aimed at
     ...plus cameraSelectedRow (the row being edited, which is NOT necessarily the
     row being previewed), cameraTargetManual/cameraTargetOverride,
     cameraNewId/cameraNewType, and showCamerasPanel. Rules:
       - Selecting a different row while previewing = updateCameraPreview, never
         begin/end, so the shot does not flicker back to the editor camera.
       - Unchecking Preview = endCameraPreview + clear cameraPreviewRow.
       - ViewportWindow::setOnCameraPreviewExit must set
         state.cameraPreviewOpen = false (the viewport self-exits on any
         navigation gesture; see section 6).
       - Closing/reloading a stage or switching zone MUST endCameraPreview first:
         cameraPreviewRow indexes a table that is about to be replaced. Same
         class of bug as the stale row indices applyRowEdit defends against.
       - Row removal shifts indices: re-validate cameraPreviewRow against
         table.size() every frame you use it, exactly like gui_win32.cpp:769
         does for viewportSelected/selectedObject.

 8.4 WHAT THE PANEL SHOWS (LaunchCamPlus' mental model, our UX)
     - List of cameras: describeCameraId(parseCameraId(cam.id)) as the label,
       camtype resolved via cameraTypeInfo/resolveCameraType for display, plus
       the context from cameraContextLabel. Keep raw id visible too - modders
       grep for it.
     - Per field: cameraFieldSpecs() in order, filtered by
       cameraFieldApplies(spec.scope, cam.context), grouped by spec.group, using
       spec.label + spec.tooltip. A column the sparse file does not store shows a
       DIM name (nothing is hidden: the widget still shows the value the row
       solves with), and hovering it gives the exact engine default for this
       row's version. That distinction is the single most useful thing in a BCAM
       editor, because a value the file omits can differ per version.
     - A support badge, shown as "Pose: exact | approximate | not reproducible
       outside the game", taken from the PoseSupport the solver reported. "none"
       is NOT an error - it means the type is dynamic-only in game.
     - Editing any camera field goes through edit::mutateCameras (section 4) and
       then updateCameraPreview with the freshly solved pose. Label the undo
       entry with the field name ("Set fovy"), and do not push one entry per
       slider frame: mutateCameras already no-ops when nothing changed, but a
       dragged ImGui slider fires constantly - commit on release, or debounce by
       comparing against the last applied value.

 8.5 BUILD + PROOF
     Build both toolchains, run the tests, then the manual pass. What THIS
     session verified, in out-of-tree builds (see section 2): MinGW Release and
     MSVC Release (VS2026 toolset via vcvars + Ninja) both built with zero new
     warnings, ctest passed on both, and the GUI opened the SMG2BigGalaxyMap
     template with the panel forced open without a crash (a 20-second smoke
     run: process stayed alive, no exception - the interaction checks below
     still need a human with a mouse):
       1. Open a SMG2 map with a camera table (a mission stage). An empty table is
          NORMAL for many stages: loadFromArchive (stage_archive.cpp:175) always
          builds an empty table stamped with the right engine version, and it
          SILENTLY swallows a corrupt CameraParam.bcam via try/catch back to that
          empty table. So "0 cameras" in the panel can mean no file, an empty
          file, or a corrupt one - do not show an error, show "no cameras".
       2. Preview an EYEPOS_FIX row: the image should not move when you change
          dist (the eye is pinned) and should swing when you change wpoint.
       3. Preview a FOLLOW row, change fovy 45 -> 90: the framing must widen and
          clicks must still land on the object under the cursor (proves the

       4. Set roll != 0 on an XZ_PARA: horizon tilts, picking still aligns, and
          the scene is not sheared (proves the orthogonal-roll projection).
       5. Click in the viewport: preview must exit, camera must be EXACTLY where
          it was (compare the target/distance readout before and after).
     If 3 or 4 fails, the bug is in camera.cpp, not the panel.

9. THE TARGET DECISION (decided), PLUS WHAT IS STILL OPEN
--------------------------------------------------------------------------------

 solveGameCameraPose takes `target` = "the point the game tracks (Mario's
 position for c:/s:/g:/o: cameras)". The editor has no running Mario, so the
 panel must supply something. The solver is honest about it: pivot = target +
 woffset, and point-fix style types aim AT target. Whatever you pick moves every
 spherical/exact preview, so it must be visible and user-changeable, never
 hidden magic.

 Options, best first:
   a) Selected object's position, else the nearest StartObj/PlayerStart, else the
      origin - PLUS an explicit "Target" XYZ triplet in the panel the user can
      override. Recommended. SHIPPED, as cameraTargetChoice(): the manual
      override wins, then the selected object, then the first placement row that
      looksLikeStartObject (kind "start", or a name like StartObj/PlayerStart/
      Mario ignoring case), then the origin. The panel ALWAYS shows the resolved
      point and its source, and the last solve's target is cached in
      cameraPreviewTarget.
   b) StartObj/PlayerStart only (PlacementObject rows named like a start).
      Closest to the game, but most stages will resolve to the origin anyway.
   c) Origin always. Simplest, least useful; fine as option (a)'s fallback.
 Whatever you choose, SHOW the resolved target next to the PoseSupport badge. A
 preview that silently frames nothing looks exactly like a broken solver, and
 this feature will get "the preview is wrong" reports that are really "the target
 is the origin" reports.

 PlacementObject comes from state.stage->objects() (iterating example at
 gui_win32.cpp:645; refreshViewport rebuilds ViewportScene from it at :736).
 Resolve names through db/name_table + db/object_db before string matching.

 Still open (do not "fix" these without asking):
   - Per-zone tables: StageArchive loads ONE CameraParam.bcam per open map file,
     so "zone" is currently "the map file you opened". A per-zone picker implies a
     StageArchive change first.
   - Screen-region columns exist in the BCAM spec but are NOT modelled in
     CameraPreviewParams, so the preview does not crop to the game's screen
     rectangle. Deliberate: the decompiled translators apply it after the pose.
     If someone adds it, it belongs in the projection, not in eye/at.
   - SMG1 rows default several fields differently; hasColumn() is the only
     trustworthy answer. Never render a defaulted 0 as if it were authored.
   - CAM_TYPE_ANIM / RAIL_DEMO / cutscene types are keyframed over time and the
     solver reports none. Grey them out with the badge; do not hide them. A time
     slider + key sampling is its own feature.
   - `roll` is passed straight through as radians. Whether the game treats it as
     camera-local or screen-space was inferred from the translators, not verified
     on hardware. If a runtime capture ever disagrees, the fix is one line in the
     solver plus one test, not a rework.

10. TOOLING TRAPS THAT COST REAL TIME (read before typing a command)
--------------------------------------------------------------------------------

 - This shell is Windows PowerShell. `&&` is NOT a statement separator - use ';'
   or separate calls. Quote paths that contain spaces. Do not wrap a command in
   another powershell.exe -Command.
 - git is NOT on PATH here. Call it as:
       & 'C:\Program Files\Git\cmd\git.exe' --no-pager <args>
   Always --no-pager, or the call hangs on a pager.
 - Build with out-of-tree directories and the recipe in section 2 (never a
   checked-in tree): devkitPro's make is gone, cmake uses Ninja instead, and a
   stale in-repo build dir would dirty hundreds of tracked files on every
   compile.
 - MSVC needs the machine's vswhere on PATH before vcvars: older sessions had a
   working VS2022, but this machine's VS2022 lost vcvarsall.bat AND the VS
   Installer (no vswhere), so cmake reports "could not find any instance of
   Visual Studio". What works is VS2026's vcvars64.bat plus
   C:\Program Files (x86)\Microsoft Visual Studio\Installer on PATH.
 - A single shell command is killed after ~30 seconds, INCLUDING its output, so
   a first full build never finishes in one call. Run the build detached via
   Start-Process (a .cmd that redirects to a log file) and poll the log. Do not
   fight it by repeating foreground builds: each kill restarts ninja's in-flight
   compiles and truncates .ninja_log ("premature end of file; recovering"),
   which then rebuilds the same files over and over.
 - Do not wrap a PowerShell command that needs cmd separators in another
   powershell.exe -Command: PowerShell 5.1 has no && operator, and cmd /c with
   embedded quotes inside a PowerShell string mangles the call. For batch
   helpers, write a .cmd file with the editor tool (with cmd-style quoting),
   not by assembling quoted strings in PowerShell.
 - Do not rewrite source files with PowerShell Set-Content/Out-File - it can
   change encoding and line endings. Use the editor tool.
 - The edit tool is chunk-limited (~6k chars per call). For a long document,
   several inserts at known line numbers beat one big write - and re-check the
   line count between inserts, because every insert shifts all later numbers.
 - The file on disk is UTF-8 (the /utf-8 compile flag is there for a reason), but
   PowerShell prints the Japanese camtype jpNames as mojibake. That is a console
   rendering artefact, NOT corruption - verify with the editor tool before
   "fixing" it. This exact false alarm already happened once here.
 - A carried-over context summary is a SUMMARY, not ground truth. When it
   disagrees with the header, the header wins, and that is why section 4 exists.
   Re-read a signature before you call it; guessing an API is how the reverted
   draft happened.
